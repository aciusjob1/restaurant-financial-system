# Phase 17.6 — Manager Recording UI

**Status:** SCOPE LOCKED — implementation pending
**Predecessor:** Phase 16B (Reports UI — read-only)
**Successor:** Phase 18 (Waiter Kiosk), Phase 19 (Electron Desktop Integration)
**Authoritative for:** the entire manager/owner write-side UI surface of the desktop app.

---

## 1. Purpose

Phase 16B delivered the **read side** of the desktop application: seven
report pages and a dashboard, all fetching server-derived values from the
Reports API. It did not deliver any mechanism by which an operator can
*create* the data those reports display.

Phase 17.6 closes that gap. It gives every **manager- and owner-facing
write workflow** a browser-reachable entry point, backed by the existing
Express + Prisma endpoints — no backend changes required except when a
genuine gap is discovered (see §10).

The result after 17.6: a manager can run a full business day inside the
desktop app without touching curl, Postman, or the database directly.

operations use a mutation hook (see §7) because forms have submit, loading,
success, and error states that reads do not.

## 7. Mutation & Error Handling

`useMutation<TInput, TOutput>` follows the same contract as `useReport`:

- Takes a path, a method, and a submit function returning `Promise<TOutput>`.
- Returns `{ status, data, error, submit, reset }`.
- On `401` — redirect to `/login`.
- On `403` — render inline error, never redirect (user is authenticated,
  just not authorized).
- On `400` / `409` / other `ApiError` — display `error.code` and
  `error.message` in the form.
- Never swallows errors silently.

Every form submits through `apiFetch` from `lib/api.ts`. No ad-hoc `fetch`
calls.

Every destructive or irreversible action (`post`, `cancel`, `approve`,
`void`, `reopen`) shows a `ConfirmDialog` first. The dialog names the
concrete entity (`Post invoice INV-0042?`) rather than a generic prompt.

Success is surfaced by navigating away, or by showing an inline green
confirmation — never a modal toast. No notification library.

## 10. Backend Discovery Rule

If, while building a 17.6 page, it becomes clear that an existing endpoint
**cannot safely support the intended UI** — for example, a required field
is missing from the response, or a validation rule prevents a legitimate
operation — the rule is:

1. **Stop.**
2. Document the specific gap in this file under a new section 11.
3. Surface the gap to the project owner.
4. Do **not** silently modify `backend/src/**`.

This keeps the 237/237 invariant as a real gate rather than an aspiration,
and ensures any backend change is a deliberate decision, not a drifting
patch.

## 15. Addendum — Expense identity model (M4)

**Date:** 2026-09-26 (during M4 build)
**Status:** LOCKED — implemented and tested

While building the Expenses page in M4, two gaps in the Expense model
surfaced that warranted a backend change under the §10 discovery rule.

### 15.1 Three separate identities on Expense

Expense now distinguishes three different people, matching the reality
of who enters, who pays, and who authorizes:

| Field | Meaning |
|---|---|
| `createdBy` | User who entered the expense into the system |
| `paidByUserId` (NEW) | User who physically paid the money |
| `approvedBy` | User who authorized the expense |

`paidByUserId` is `String?` with `onDelete: Restrict`. It is optional.
Existing rows remain valid with `paidByUserId = NULL`.

Rationale: a manager can record an expense on behalf of a cashier who
handed over the receipt. Pretending the manager was the payer would
corrupt the audit trail. `createdBy` and `paidByUserId` are different
facts and are now both recorded.

`employeeId` — the "which employee was this for" question — is
deliberately **not** added here. Employee-related payments (salaries,
advances, reimbursements) belong in their own employee/salary module
with a proper payroll structure, not bolted onto the generic Expense.

### 15.2 OWNER self-approval exception

The self-approval rule (`SELF_APPROVAL`) is relaxed **only for OWNER**:

- **OWNER** may create, submit, and approve their own expense.
- **MANAGER** still cannot approve their own expense (409 `SELF_APPROVAL`).

In a small restaurant there is no one above the OWNER. Blocking their
own authorization forced them to route around the rule, which is worse
for the audit trail than the exception.

The exception must be **explicit in the record**, not implied. The
serializer now emits `selfApproved: boolean`, derived server-side:

    selfApproved = approvedBy !== null && createdBy === approvedBy

Clients cannot supply or override this field. If an OWNER approves their
own expense, the record shows `selfApproved: true` — honest about the
one-person signature rather than pretending two people signed off.

### 15.3 New error code

- `400 INVALID_PAID_BY` — `paidByUserId` references a user that does not exist.

### 15.4 Files changed

| Layer | File | Change |
|---|---|---|
| Schema | `backend/prisma/schema.prisma` | `Expense.paidByUserId` + `User.paidExpenses` relation |
| Migration | `20260926112057_phase17_6_expense_paidby` | adds nullable column + FK with `onDelete: Restrict` |
| Validator | `backend/src/validators/expense.ts` | `paidByUserId` on Create + Update schemas |
| Service | `backend/src/services/expenseService.ts` | accept `paidByUserId`; validate FK; relax `SELF_APPROVAL` for OWNER; emit `selfApproved` and `paidByUserId` in serialize |
| Controller | `backend/src/controllers/expenseController.ts` | forward `paidByUserId` |
| Frontend | `frontend/app/ops/expenses/page.tsx` | "Paid by" dropdown + table column; role-aware Approve/Reject; loads `/api/v1/users` for the name map |
| Tests | `backend/tests/expenseSelfApproval.test.ts` (new) | 6 cases: OWNER self-approve OK, MANAGER self-approve 409, cross-approve sets `selfApproved:false`, paidByUserId round-trips, null path, invalid paidByUserId 400 |

- `pnpm --filter @rfs/backend typecheck` — 0 errors
- `pnpm --filter @rfs/backend test` — **243 / 243**

### 16.3 API contract verified end-to-end

Before closing M5, both endpoints were exercised through real HTTP
calls (not just tests):

| Call | Result |
|---|---|
| POST `/sales-summaries` (CASH 1234.56 + MPESA 789.00) | 409 `NO_ACTIVE_SHIFT` — business rule fires correctly (no shift open for the target date) |

The 409 `NO_ACTIVE_SHIFT` is correct behavior, not a bug — sales
summaries require an open shift for the business date.

### 16.4 The `apiFetch` JSON-body gotcha

The shared helper `frontend/lib/api.ts` passes its second argument
directly to `fetch()` — meaning `body` must be a JSON **string**, not a
plain object. Both pages initially sent `body: { ... }` (which
serializes to `"[object Object]"`). Fixed to `body: JSON.stringify({...})`.

**Follow-up for future pages:** any POST/PATCH in this codebase must
send `body: JSON.stringify(payload)`.

### 16.5 Deferred: `CONSUMPTION + IN`

The stock-movement backend currently accepts any `type` × `direction`
combination, including `CONSUMPTION + IN` and `OPENING + OUT`. The M5
UI defaults a sensible direction per type (OPENING→IN, CONSUMPTION→OUT,
WASTE→OUT, ADJUSTMENT→IN) but the backend does not enforce it.

**Decision:** defer. This is a legitimate business rule but tightening
it would turn a closed frontend milestone into an unplanned backend
sub-phase. Recorded as a validation candidate; revisit when the full
stock-movement workflow is in context.

### 17.3 What the backend already did (discovered during M6-A)

- **Invoice totals**: `POST /purchase-invoices` sets `subtotal = total`.
  `PUT /:id/items` recomputes both from item sums. Posting enforces
  `itemSum === total` and refuses otherwise (`LINE_TOTAL_MISMATCH`).
- **Posting** (`POST /:id/post`): requires DRAFT, requires items,
  updates `Material.currentPrice` to each item's unit price, creates
  one PURCHASE / IN stock movement per materialised item, sets
  POSTED. Refuses on a closed business day.
- **Cancellation** (`POST /:id/cancel`): only POSTED → CANCELLED,
  refuses if active allocations exist (`HAS_ACTIVE_ALLOCATIONS`),
  emits reversing ADJUSTMENT / OUT movements. Deliberately does **not**
  roll back `Material.currentPrice` (covered by test).
- **Allocation limits** (`POST /:id/allocations`): enforces
  `sum(active) <= payment.amount` (`PAYMENT_OVERALLOCATED`) and
  `sum(active) <= invoice.total` (`INVOICE_OVERALLOCATED`), plus
  `SUPPLIER_MISMATCH` and `INVOICE_NOT_POSTED` guards. Uses
  Serializable isolation with P2034 retry.
- **Voiding a payment** cascades to its active allocations.
- **Supplier balance** excludes CANCELLED invoices and voided
  payments/allocations. Returns balance, invoiced, paid, allocated,
  unallocated.

### 17.4 What M6 added (frontend)

- Supplier-name lookup on the invoices list (same pattern as M4's
  paid-by resolution — the serializer returns `supplierId`, not name).
- Items editor on the invoice detail: editable rows, material
  dropdown, live-computed items subtotal, amber warning when the
  current items sum differs from the saved invoice total.
- Status-aware action strip: DRAFT shows Post + Delete; POSTED shows

- Payment detail: allocation form (POSTED+unpaid invoices only),
  live "total allocated / remaining on payment" display, per-row
